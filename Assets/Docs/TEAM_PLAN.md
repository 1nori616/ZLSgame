# 团队协作方案（ZLSgame · 重力操控横板动作）

> 依据：《2026 零基础游戏开发实训 · 学习路线与岗位课题》里的角色要求、课题与提交自检。
> 目标：让三个人在**同一套交付物**上并行，而不是"各画各的、各写各的"。

## 0. 一句话项目定位

> 一款 2D 横板动作游戏：玩家不能挥刀，只能**改变重力**——把敌人飘起来、砸下去、连段压制。

所有设计、美术、代码都围绕这一句判断取舍。

## 1. 三个角色分别交付什么

| 角色 | 交付物 | 形式 | 谁接收 |
|---|---|---|---|
| 策划 | **机制卡**（一页） | `Docs/Design/机制-xxx.md` | 程序 |
| 策划 | **关卡白盒**（纸面网格 + 标注） | 图片 + 说明 | 程序 → 美术 |
| 美术 | **风格板**（色板、线条、光源方向） | 一张图 | 全员 |
| 美术 | **资产包**（角色/敌人/场景贴图） | `Assets/Art/` + 源文件 | 程序 |
| 程序 | **可玩版本** | 打包 exe + 仓库 | 全员 |

**关键原则**：交付物是"别人能直接用的东西"，不是"我做完的东西"。

## 2. 策划怎么配合

### 2.1 机制卡模板（每个机制一页）

```markdown
# 机制：重力连段

## 一句话体验
按住节奏把敌人反复抛起砸下，越连越痛。

## 玩家做什么（不是"世界是什么"）
1. 面朝敌人按 Q → 敌人上浮
2. 上浮期间按 E → 立刻下坠砸地
3. 2.5 秒内重复 → 伤害递增

## 反馈
- 视觉：震屏、冲击波、闪白、压扁
- 数值：1 → 1.5 → 2 倍伤害
- 音效：（待补）

## 数值表
| 项 | 值 | 理由 |
|---|---|---|
| 上浮最高速 | 5 | 太低看不出来，太高飞走 |
| 连段窗口 | 2.5s | 刚好够追一步 |
| 冷却 | 3 格充能 / 1.2s | 能连，但不能无脑 |

## 验收标准（怎么算做对了）
- 站着连按 3 次，敌人被压在地上起不来
- 打空 1 次后节奏断掉，必须重新起手

## 不做（范围控制）
- 不做多目标同时施放
```

> 手册原话："先写玩家做什么，再写世界是什么"；"每条设计判断都给验证方式"。

### 2.2 关卡设计三段式

1. **纸面**：网格纸画平台高度、敌人位置、尖刺位置，标注"这里想教玩家什么"
2. **白盒**：程序按纸面在 Unity 里摆方块（`Assets/Scenes/Level_xx.unity`）
3. **贴图**：美术把白盒替换成正式素材

**地图设计的最小单位是"一个房间"**：入口 → 教学点（一个机制）→ 压力点（组合）→ 出口。

### 2.3 交付节奏

- 每周一：交 1 张机制卡 + 1 张关卡纸面
- 每周五：验收上周机制在游戏里是否成立，写 3 行结论

## 3. 美术怎么配合

### 3.1 先做风格板（半天，不要跳）

一张图定死：色板（5~7 色）、线条粗细、光源方向、像素密度（每单位多少像素）。

**没有风格板就开画 = 后面全部返工。**

### 3.2 资产规范（交付前必须满足）

| 项 | 规范 |
|---|---|
| 画布 | 同一套资产用同一画布尺寸（如主角 64×64，敌人 48×48） |
| 像素密度 | `Pixels Per Unit = 100`，全项目统一 |
| 命名 | `角色_动作_帧号.png`，如 `Player_Run_03.png` |
| 枢轴 | 角色脚底中心（Pivot = Bottom） |
| 透明 | 背景透明，无多余留白 |
| 源文件 | `.psd` 保留分层，只提交导出图，源文件走 LFS |

### 3.3 交接给程序前，自己先在 Unity 里看一眼

手册原话："已在 Unity 内预览，而不是只看绘图软件。"

**验收动作**：把图拖进场景，`Sprite Renderer` 里看比例、光照、枢轴对不对。

### 3.4 本项目需要的资产清单

| 类别 | 内容 | 优先级 |
|---|---|---|
| 主角 | idle / run / jump / fall / dash / hurt | P0 |
| 敌人 | walk / hurt / 被压扁姿态 | P0 |
| 场景 | 地砖（可平铺）、平台、尖刺、背景远景 | P1 |
| UI | 血条底+填充、重力充能 3 格、连段数字 | P1 |
| 特效 | 冲击波环（已有代码版，可选替换） | P2 |

## 4. 程序（我）怎么配合

1. **把机制卡变成参数**：所有机制数值进 `PlayerConfig`，让策划自己调
2. **把白盒变成可玩**：关卡只用方块搭，不依赖美术，先验证玩法
3. **把资产接上**：美术交付后，替换 `Sprite Renderer`，不改逻辑
4. **每周给一个可玩包**：打包 exe 发群里，让他们用真机试

## 5. 两周节奏（可调整）

| 周 | 策划 | 美术 | 程序 |
|---|---|---|---|
| 第 1 周 | 机制卡 ×2（重力连段、受击反馈）+ 第 1 关纸面 | 风格板 + 主角 idle/run | 关卡白盒 + 敌人受击反馈 |
| 第 2 周 | 第 1 关白盒验收 + 数值调优 | 主角 jump/fall/hurt + 敌人 walk | 接入主角动画 + 打包 v0.2 |

**周五固定 30 分钟同步**：看包、提问题、定下周。

## 6. 对齐课程提交要求（作业别丢分）

| 角色 | 手册要求 | 怎么做 |
|---|---|---|
| 程序 | 可打开工程 + 主场景能跑 + 无 Library/Temp/Logs | 本仓库已满足；打包 exe 另存 |
| 策划 | 拆解案有结论、图表有来源、30 秒能看懂 | 拆《死亡细胞》/《水果忍者》，结论直接用于本项目机制 |
| 美术 | 尺寸/命名/风格统一、Unity 内预览过 | 按 3.2 规范执行 |
| 队长（你） | 组织一次 30 分钟规范同步、确认每人能 clone/pull | 用 `ONBOARDING.md` 开一次会 |

**省力技巧**：让**课题和项目对齐**——

- 美术课题选"角色全套状态机动画"，直接产出主角
- 策划课题选"拆解一款游戏"，拆的就是你要做的类型

一份工，两份交付。

## 7. 最容易翻车的三件事

| 翻车点 | 手册原话 | 预防 |
|---|---|---|
| 策划写"是什么"，没写"为什么好玩" | 只交描述，不交判断 | 机制卡必须有"验收标准" |
| 美术只在绘图软件里好看 | 进 Unity 后比例/光照/枢轴全错 | 交付前必须 Unity 预览 |
| 程序只交了 Build | 没有可打开的工程 | 仓库本身就是交付物 |

## 8. 每天的同步方式

- 不开发时会，只在群里发一条：`今天做：xxx / 卡在：xxx`
- 谁改了公共文件（场景、PlayerConfig、Prefab），提前在群里说一句

> 一句话总结：**策划给"判断"，美术给"资产"，程序给"能玩的东西"，三者都必须在仓库里，而不是在各自电脑里。**
